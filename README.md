## Проблема
Студентам и преподавателям сложно контролировать процесс код-ревью в командной разработке. Разработчики теряют время на ручное назначение ревьюеров для Pull Request’ов, а нагрузка распределяется неравномерно. Часто участники пропускают задачи или уведомления о новых PR, что замедляет процесс проверки кода.

## Выработка требований 
Пользовательские истории

История 1 (разработчик):
**Когда** я создаю Pull Request в репозитории, **я хочу** чтобы нужный ревьюер был назначен автоматически, **чтобы** мне не приходилось тратить время на ручной выбор и PR попал к подходящему человеку.

История 2 (ревьюер):
**Когда** появляется новый Pull Request, **я хочу** получать уведомление через Telegram, **чтобы** вовремя ознакомиться с изменениями и не пропустить задачи, требующие проверки кода.

История 3 (тимлид / руководитель):
**Когда** несколько Pull Request создаются одновременно, **я хочу** чтобы каждому PR автоматически назначался ревьюер, выбранный случайным образом (исключая автора), **чтобы** процесс проверки PR происходил без ручного выбора, а нагрузка распределялась приблизительно случайным образом между участниками команды.
- Примерное количество пользователей: ~10000 зарегистрированных участников (разработчики + тимлиды + ревьюеры)
- Активные пользователи в сутки: 30-40% (3000 - 4000 пользователей/сутки)
- Среднее количество PR в сутки: ~1000-1500
- Период хранения данных: ≥ 5 лет (для PR и назначений)

## Разработка архитектуры и детальное проектирование

### Характер нагрузки на сервис
Сервис предназначен для автоматической обработки событий Pull Request из GitHub и выполняет следующие операции:
- прием webhook-событий;
- сохранение информации о PR;
- выбор и назначение ревьюера;
- отправка уведомления в Telegram.

Нагрузка носит событийный характер и напрямую зависит от количества создаваемых Pull Request’ов. Пиковая активность наблюдается в рабочее время (будние дни, 10:00–18:00).

Ожидаемая нагрузка:
- Pull Request’ы: ~1000-1500 в сутки
- Пиковая нагрузка: до 5-10 запросов в секунду
- Тип нагрузки: нерегулярная, с короткими всплесками

#### Соотношение R/W нагрузки
В данном проекте соотношение записи к чтению - примерно 60% на 40%. Соотношение считается от операций с базой данных, которые выполняются на одно бизнес-событие.

В нашем сервисе таким событием является создание Pull Request (PR)

Мы считаем: 
- сколько чтений (SELECT) выполниться на 1 PR
- сколько записей (INSERT) выполниться на 1 PR

При поступлении webhook pull_request opened сервис выполняет:
- Определение репозитория (ensureRepository) - WRITE.
- Сохранение PR (SavePullRequest) - WRITE.
- Выбор ревьюера (SelectReviewer) - READ.
- Назначение ревьюера (AssignReviewer) - WRITE.
- Получение Telegram chat_id (NotifyReviewer) - READ.

Итого, событие создание Pull Request:
- Read - операций : 3 операций (60%)
- Write - операций : 2 операций (40%)
- Общее количество: 5 операций на одно событие (Создание PR)

#### Объемы трафика
- Средний размер GitHub webhook payload: 3-5 KB
- При 1500 PR в сутки: входящий трафик ~7-8 MB/сутки
- Ответ сервиса: минимальный (HTTP 200 OK, < 1 KB)

#### Объемы дисковой системы
Оценка хранения данных:
- pull_requests - ~200-300 байт на запись
- review_assigments - ~100 байт на запись

При хранении данных более 5 лет:\
- ~474500 PR в год 
- ~2372500 PR за 5 лет
- общий объем данных < 930 - 980 MB
  
PostgreSQL без проблем выдерживает такие объемы даже без дополнительной оптимизации.

### Контракты API и нефункциональные требования

API контракты 
- GET /health
Проверка доступности сервиса
Ответ: 200 OK
- POST /github/webhook
Приём событий Pull Request от GitHub
Ответ: 200 OK

Нефункциональные требования
- Время обработки webhook: < 100 ms
- Поддержка нагрузки до 10 RPS
- Надежное хранение данных > 5 лет
- Отказоустойчивость на уровне перезапуска сервиса

### Схемы базы данных и обоснование

Основные таблицы: 
- users - пользователи и Telegram chat_id
- repositories - репозитории
- pull_requests - Pull Request’ы
- review_assigments - назначение ревьеверов

Почему БД выдержит нефункциональные требования:
- простая реляционная схема;
- небольшие объемы данных;
- PostgreSQL оптимизирован для частых операций чтения и записи.

### Масштабирование при росте нагрузки в 10 раз

При увеличении нагрузки до: 
- ~15000 PR в сутки
- ~50-100 RPS

Основные точки нагрузки:

  Go HTTP сервер 
  - обработка webhook’ов
  - сериализация JSON
	
  PostgreSQL
  - SELECT + INSERT при каждом PR
